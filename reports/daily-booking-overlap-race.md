## Executive Summary

ผู้เช่าที่ล็อกอินแล้วในบทบาท `tenant` เช่น Mallory สามารถส่งคำขอ `POST /bookings` แบบเช่ารายวันสองคำขอพร้อมกัน โดยระบุห้องและช่วงวันเดียวกันได้ เมื่อห้องนั้นว่าง (`AVAILABLE`), ผ่านการอนุมัติ, อยู่ในหอที่อนุมัติแล้ว และเปิดให้เช่ารายวัน การจองรายวันควรมีได้เพียงรายการเดียวต่อห้องในช่วงวันที่ทับซ้อนกัน แต่การตรวจช่วงวันและการสร้างรายการเป็นคำสั่งฐานข้อมูลคนละคำสั่ง จึงมีช่วงเวลาที่ทั้งสองคำขออาจไม่พบรายการเดิมก่อนจะสร้าง `Booking` ของตนเองได้ ผลกระทบที่หลักฐานซอร์สรองรับคือรายการจองรายวันสถานะใช้งานได้ที่ช่วงวันทับซ้อนกันมากกว่าหนึ่งรายการ ซึ่งเสี่ยงให้เกิดการจองห้องซ้อนและการจัดการที่พักผิดพลาด ไม่ใช่การยึดบัญชี การขโมย session หรือการขโมยเงินจากการชำระเงิน

ประเมินจากซอร์ส revision `61b27ceaa1e768a40ed81e945c7822f8073cac3e` ซึ่งไม่มี Git tag ที่ใช้ระบุรุ่นเผยแพร่ได้ การตรวจช่วงวันถูกเพิ่มพร้อมฟีเจอร์เช่ารายวันใน commit `fbb4fff` และยังคงเป็นการอ่านแล้วเขียนแยกกันใน revision ที่ประเมิน ไม่พบ tag, release snapshot หรือแก้ไขที่ยืนยันได้ จึงไม่อาจระบุรุ่นแรกที่ได้รับผลกระทบ ช่วงรุ่นที่ได้รับผลกระทบ หรือรุ่นที่แก้ไขแล้วได้

ผมตรวจซอร์ส revision ที่ระบุ, ประวัติของโค้ดและ migration ที่เกี่ยวข้องโดยตรง แต่ไม่ได้รันคำขอแข่งกันหรือ PoC กับระบบใด ผลลัพธ์เชิงเวลาในรายงานจึงเป็นพฤติกรรมที่คาดจากซอร์ส ไม่ใช่ผลการทดสอบที่สังเกตได้

## Background

เส้นทางสร้างการจองอยู่ที่ `apps/api/src/modules/bookings/bookings.controller.ts`, method `create` ใน revision ที่ประเมิน ตัว controller ใช้ JWT guard และจำกัด method นี้ไว้ที่บทบาท `tenant` ก่อนส่ง `user.id` และ DTO ให้ `BookingsService.create`:

```ts
@Post()
@Roles('tenant')
@UseGuards(RolesGuard)
create(@CurrentUser() user: { id: string }, @Body() dto: CreateBookingDto) {
  return this.bookingsService.create(user.id, dto);
}
```

`CreateBookingDto` ใน `apps/api/src/modules/bookings/dto/create-booking.dto.ts` อนุญาต `rentalType` เป็น `DAILY` และรับ `roomId`, `checkInDate` และ `checkOutDate` ได้ สำหรับเส้นทางรายวัน `BookingsService.create` ยังตรวจว่าห้องว่างและผ่านการอนุมัติ หอผ่านการอนุมัติ และ `createDaily` ตรวจ `allowDaily` กับวันคืนห้องก่อนทำงานต่อ ดังนั้น Mallory ต้องเป็นผู้เช่าที่มีสิทธิ์และเลือกห้องที่เปิดให้จองจริง ไม่ได้อาศัยสิทธิ์ของเจ้าของหอหรือผู้ดูแลระบบ

ช่วงวันใช้วันคืนห้องเป็นขอบเขตแบบไม่รวมวันคืนห้อง: การจองที่เริ่มในวันซึ่งรายการก่อนหน้าคืนห้องไม่ควรถูกนับว่าทับซ้อนกัน ขณะที่รายการสถานะอื่นนอกจาก `CANCELLED` ควรกันช่วงวันนั้นไว้

## Vulnerability Details

ใน `apps/api/src/modules/bookings/bookings.service.ts`, `BookingsService.create` ส่งคำขอที่มี `rentalType === 'DAILY'` ไปยัง `createDaily` หลังการตรวจห้องทั่วไป:

```ts
const rentalType = dto.rentalType ?? 'MONTHLY';
if (rentalType === 'DAILY') {
  return this.createDaily(tenantId, room, dto, now);
}
```

`createDaily` ตรวจการทับซ้อนด้วยเงื่อนไขที่ถูกต้องสำหรับขอบเขตวันแบบข้างต้น แล้วจึงปฏิเสธเมื่อพบรายการเดิม:

```ts
const overlap = await this.prisma.booking.findFirst({
  where: {
    roomId: room.id,
    rentalType: 'DAILY',
    status: { not: 'CANCELLED' },
    checkInDate: { lt: checkOut },
    checkOutDate: { gt: checkIn },
  },
});
if (overlap) throw new BadRequestException('ช่วงวันที่เลือกถูกจองแล้ว กรุณาเลือกวันอื่น');
```

นี่อธิบาย negative control แบบลำดับต่อเนื่องได้: หลังรายการแรกถูก commit แล้ว คำขอใหม่ที่ใช้ห้องและช่วงวันที่ทับซ้อนกันควรถูก query นี้พบและถูกปฏิเสธ แต่ `findFirst` ไม่ได้จองแถว, ล็อกห้อง, หรืออยู่ใน transaction ที่ทำให้การตรวจและการสร้างเป็นหน่วยเดียว

เมื่อไม่พบ `overlap` โค้ดเรียก `booking.create` ใน `await` ถัดมา:

```ts
const booking = await this.prisma.booking.create({
  data: {
    tenantId,
    roomId: room.id,
    checkInDate: checkIn,
    checkOutDate: checkOut,
    rentalType: 'DAILY',
    status: 'PENDING',
    // ...
  },
});
```

ด้วยเหตุนี้ คำขอสองคำขอที่ผ่านการตรวจเบื้องต้นเหมือนกันอาจมีลำดับเป็น: คำขอ A อ่านแล้วไม่พบรายการ, คำขอ B อ่านแล้วไม่พบรายการ, แล้ว A และ B สร้างรายการของตนเอง ไม่มีข้อใดในสอง excerpt นี้ทำให้การอ่านของคำขอหนึ่งกันการเขียนของอีกคำขอหนึ่ง

การตรวจ schema และ migration ที่มีใน revision เดียวกันพบว่า PostgreSQL ถูกใช้เป็น datasource และ `Booking` มี `roomId`, `checkInDate`, `checkOutDate`, `rentalType` และ `status` แต่ไม่พบ exclusion constraint หรือ constraint อื่นที่บังคับไม่ให้ช่วงเวลาทับซ้อนกัน Migration `apps/api/prisma/migrations/20260803063612_daily_rental/migration.sql` เพิ่มคอลัมน์เช่ารายวันเท่านั้น การไม่มี database constraint ที่ตรวจพบนี้หมายความว่า insert ทั้งสองไม่ได้ถูกป้องกันโดยกฎช่วงวันที่ที่ตรวจในซอร์ส

ประวัติ Git ระบุว่า commit `fbb4fff` เพิ่ม `createDaily`, เงื่อนไข `findFirst` และ migration ของการเช่ารายวันพร้อมกันในวันที่ 3 สิงหาคม 2026 การเปลี่ยนแปลงหลังจากนั้นในไฟล์ service ยังไม่เปลี่ยนคู่คำสั่งตรวจแล้วสร้างนี้ใน revision ที่ประเมิน อย่างไรก็ดี repository ไม่มี tag ให้ตรวจ release จริง จึงเป็นเพียงจุดเริ่มต้นในประวัติซอร์ส ไม่ใช่การยืนยันรุ่นเผยแพร่แรกที่ได้รับผลกระทบ

## Exploitability Analysis

หลักฐานซอร์สตั้งอยู่ที่ความเป็นไปได้ของ interleaving เท่านั้น: Mallory มีบัญชีผู้เช่าที่ถูกต้องและส่งอย่างน้อยสองคำขอเช่ารายวันสำหรับห้องที่เปิดให้จองและช่วงวันเดียวกันในจังหวะที่ยังไม่มีรายการใช้งานอยู่ หากการอ่านทั้งสองเกิดก่อน insert ใด ๆ จะไม่มีผลลัพธ์ที่ `findFirst` ใช้ปฏิเสธ ทั้งสองคำขอจึงอาจไปถึง `booking.create` ได้

ผลกระทบที่แคบที่สุดคือความสมบูรณ์ของปฏิทินและ inventory ของห้อง: อาจมี `PENDING` booking มากกว่าหนึ่งรายการสำหรับห้องและคืนเดียวกัน ซึ่งขัดกับนโยบายกันจองซ้ำที่โค้ดพยายามบังคับ รายงานนี้ไม่ได้ยืนยันว่าคำขอจะชนะการแข่งขันได้อย่างสม่ำเสมอใน production เพราะยังไม่ได้วัด isolation level, scheduling, การ retry ของ client หรือพฤติกรรมฐานข้อมูลขณะใช้งานจริง และไม่ได้ยืนยันผลภายหลัง เช่น การรับชำระเงินหรือการเข้าพักจริง

การส่งคำขอซ้ำแบบต่อเนื่องไม่ใช่เส้นทางโจมตีนี้: หลัง insert แรกมองเห็นได้, predicate เดียวกันควรพบรายการ `PENDING` ที่ยังไม่ `CANCELLED` และ throw ข้อผิดพลาด การต้องใช้คำขอพร้อมกันเป็นข้อจำกัดสำคัญ ไม่ใช่หลักฐานของการเข้าถึงข้อมูลข้ามผู้ใช้หรือการยกระดับสิทธิ์

## Proof of Concept

ไม่มี PoC, log, trace หรือผลรันที่ตรวจสอบได้ในขอบเขตนี้ และไม่ได้ส่งคำขอไปยัง application ใด จึงไม่มีคำสั่งหรือ output ที่ควรตีความว่าเป็นผลสังเกต

พฤติกรรมที่คาดจากซอร์สสามารถอธิบายได้โดยไม่รันระบบ: ให้ Mallory ส่งคำขอ `POST /bookings` สองคำขอที่ผ่าน validation โดยทั้งคู่ระบุ `rentalType: "DAILY"`, `roomId` เดียวกัน และช่วง `[checkInDate, checkOutDate)` เดียวกันสำหรับห้องที่พร้อมจอง หากทั้งสอง `findFirst` เสร็จก่อน `booking.create` ครั้งแรก จะคาดว่าทั้งสองเข้าสู่คำสั่งสร้างได้; หากคำขอที่สองตรวจหลัง insert แรกมองเห็นได้ จะคาดว่าถูกปฏิเสธด้วย branch `if (overlap)` ข้างต้น ผลทั้งสองเป็นการวิเคราะห์ลำดับจากซอร์ส ไม่ใช่การยืนยัน response ของระบบ

การทดสอบ regression ที่ปลอดภัยควรใช้ฐานข้อมูลทดสอบที่แยกต่างหากและ barrier ควบคุมให้ worker สองตัวผ่านจุดตรวจในเวลาเดียวกัน หลังการแก้ไขควรยืนยันว่าได้ผลสำเร็จเพียงหนึ่งรายการ อีกคำขอได้ข้อผิดพลาด conflict ที่กำหนดไว้ และไม่มี booking รายวันใช้งานสองรายการที่ทับซ้อนกัน การทดสอบแบบต่อเนื่องควรคงไว้เพื่อยืนยันว่าการจองต่อวันคืนห้องยังทำได้และช่วงที่ทับซ้อนกันถูกปฏิเสธ

## Remediation

ย้าย invariant “ห้องเดียวกันต้องไม่มีช่วงรายวันที่ยังไม่ยกเลิกทับซ้อนกัน” ไปบังคับที่ PostgreSQL เพื่อให้เป็นจริงแม้มี application instance หรือคำขอพร้อมกันหลายตัว วิธีที่ตรงที่สุดคือ exclusion constraint ที่เทียบ `roomId` และ `tsrange(checkInDate, checkOutDate, '[)')` สำหรับ booking ที่ `rentalType = 'DAILY'` และ `status <> 'CANCELLED'`; PostgreSQL อาจต้องเปิด extension `btree_gist` เพื่อให้ใช้ equality ของ `roomId` กับ GiST ได้ Constraint ต้องถูกออกแบบให้การเปลี่ยนสถานะจาก `CANCELLED` กลับมาเป็นสถานะใช้งานถูกตรวจด้วยเช่นกัน ไม่ใช่ตรวจเฉพาะตอน create

หากใช้ constraint ดังกล่าวไม่ได้ ให้ใช้ transaction ที่ serializable หรือ lock ต่อ `roomId` ซึ่งถือ lock ตั้งแต่ก่อนตรวจ overlap จนถึงหลัง create และให้ทุกเส้นทางที่สร้างหรือคืนสถานะ booking รายวันเข้าร่วม protocol เดียวกัน การใช้ `findFirst` และ `create` ใน transaction ที่ไม่มี isolation หรือ lock ที่เหมาะสมเพียงอย่างเดียวไม่เพียงพอ ควรแปลงการละเมิด constraint หรือ conflict จาก transaction เป็นข้อผิดพลาดที่ client เข้าใจได้ และไม่ส่ง notification ว่าเป็นการจองใหม่เมื่อ insert ถูกปฏิเสธ

เพิ่ม regression test ระดับฐานข้อมูลสำหรับคำขอพร้อมกันตามลำดับที่อธิบายข้างต้น, การปฏิเสธแบบต่อเนื่อง, ช่วงวันติดกันที่ไม่ทับซ้อน, booking ที่ `CANCELLED` ซึ่งควรเปิดช่วงวันได้, และการ restore ที่พยายามทำให้กลับมาทับซ้อน การทดสอบต้องตรวจจำนวนแถวในฐานข้อมูล ไม่ใช่เพียงตรวจ HTTP response

## Summary

ในซอร์ส revision ที่ประเมิน ผู้เช่าที่มีสิทธิ์สามารถพยายามส่งการจองรายวันซ้อนพร้อมกันได้ เพราะ `BookingsService.createDaily` ตรวจ overlap ด้วย `findFirst` แล้วเรียก `booking.create` แยกกัน และ schema/migration ที่ตรวจไม่มีกฎฐานข้อมูลกันช่วงทับซ้อน หลักฐานรองรับความเป็นไปได้ของ booking ใช้งานซ้อนกันและความเสี่ยงต่อการจองห้องผิดพลาดเท่านั้น ไม่ยืนยันความน่าเชื่อถือของการแข่งขันใน production, การชำระเงิน, หรือผลกระทบข้ามบัญชี

ประวัติซอร์สชี้ว่าพฤติกรรมเริ่มพร้อมฟีเจอร์รายวันใน `fbb4fff` แต่ไม่มี release tag หรือหลักฐานแก้ไขให้ระบุช่วงรุ่นได้ การยืนยันที่มีประโยชน์ที่สุดถัดไปคือรัน regression test ควบคุม concurrency กับ PostgreSQL ที่ใช้จริงหลังเพิ่ม database invariant หรือ protocol lock ที่ครอบคลุมทุกการเปลี่ยนสถานะที่เกี่ยวข้อง
